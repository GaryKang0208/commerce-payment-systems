## commerce-payment-system
커머스 결제 시스템 프로젝트

### 주요 기술 스택

| 구분 | 기술                 |
| :--- |:-------------------|
| **Language** | Java 17            |
| **Framework** | Spring Boot 4.1.0  |
| **ORM** | Spring Data JPA    |
| **Database** | MySQL              |
| **Library** | Lombok, Spring Validation |
| **Frontend** | Thymeleaf, Bootstrap |

---

### 디렉토리 구조
```text
src
└── main
    └── java
        └── com.example.commercepaymentsystem
            ├── common          # 공통 기능 (설정, BaseEntity, 글로벌 예외 처리 등)
            ├── customer        # 고객 도메인 (인증, 프로필 관리 등)
            │   ├── controller  # API 요청 처리 및 응답 반환
            │   ├── dto         # 계층 간 데이터 교환 객체 (Request/Response 분리)
            │   ├── entity      # DB 테이블 매핑 도메인 객체
            │   ├── error       # 도메인 커스텀 에러
            │   ├── repository  # Spring Data JPA 기반 DB 접근 계층
            │   └── service     # 핵심 비즈니스 로직 및 트랜잭션 처리
            ├── payments        # 결제 도메인 (결제, 결제취소)
            ├── order           # 주문 도메인 (주문 생성, 취소, 재고 차감/복구)
            ├── cart            # 장바구니 도메인 (장바구니 생성, 취소, 일괄결제)
            └── product         # 상품 도메인 (조회, 정렬, 검색)
```

### 비즈니스 로직 및 핵심 기능

#### <span style="color:lightgreen">👤고객 (Customer) </span>
- **회원가입**
    - 이메일·비밀번호·이름·전화번호로 회원 생성
    - 이메일 중복 검증 및 비밀번호 암호화

- **로그인**
    - 이메일·비밀번호 검증 및 JWT 발급
    - Bearer 방식으로 토큰 전달

- **인증·인가**
    - JWT 기반 인증 처리
    - 주문·장바구니·결제·포인트 API 접근 제어

- **소유권 검증**
    - 본인 주문·결제·포인트만 조회 및 처리
    - 타인 접근 시 403 Forbidden 처리

- **예외 처리**
    - 인증 실패 시 401 Unauthorized
    - 이메일 중복 가입 차단시킵니다. 회원 탈퇴는 전용 API(Soft Delete)를 통해서만 안전하게 수행되도록 역할이 분리되어 있습니다.

<br>

#### <span style="color:lightgreen">🖩결제 (Payments) </span>
- **모의 결제**

    - 본인 소유 주문인지, 주문 상태가 '결제대기' 상태고 결제 상태가 '대기' 상태인지, 요청 금액이 서버가 저장해 둔 결제 금액과 일치하는지 검증합니다.
    - 주문 금액은 항상 DB의 결제 레코드에서 읽고, 클라이언트가 보낸 값은 비교용으로만 사용하여 결제 사고를 막습니다.
    - 이미 완료 또는 실패인 결제에 다시 요청이 오면 상태를 바꾸지 않고 4xx를 반환합니다.
    - 
- **결제 결과**

    - 결제에 성공하면 결제 상태를 완료로 변경하고 주문 상태를 주문 왼료로 변경합니다. 또한, 장바구니를 비웁니다.
    - 결제에 실패하면 감소시켰던 재고를 원복합니다.
  
- **결제 취소기능**
    - 본인 소유의 주문인지, 취소 가능한 상태인지 검증합니다.
    - 타인의 주문을 취소하려고 시도 시 403 Forbidden을 반환합니다.
    - 결제 전/후에 따라 결제 상태를 결제 '취소'/'환불'로 다르게 전이시킵니다.
    - 재고 복구까지 하나의 트랜잭션으로 처리합니다.
    - 결제 취소 시 **포인트 사용 유무에 따른 환급조치**를 최우선으로 취소 절차를 진행합니다.

<br>

#### <span style="color:lightgreen">🛒장바구니 (Cart) </span>

- **장바구니 데이터 제어 및 도메인 검증**
    - 로그인 회원의 장바구니는 1개만 존재하도록 보장하며, 최초 상품 담기 시점에 없으면 자동 생성합니다.
    - 동일 상품을 다시 담을 경우 행 추가 없이, 기존 항목의 수량에 합산하여 **중복 저장을 방지**합니다.
    - 담기·수량 변경 결과가 상품 재고를 초과하면 도메인 예외(OUT_OF_STOCK)를 발생시켜 저장을 차단합니다.

- **소유권 검증**
    - 모든 장바구니 API는 회원 ID를 기준으로 **본인 소유 항목에만 접근**도록 제한합니다.
    - 타인의 장바구니 항목에 대한 수정·삭제 시도는 도메인 예외(FORBIDDEN_CART_ACCESS)로 차단합니다.

<br>

#### <span style="color:lightgreen">🧾주문(Order)</span>

- **주문 생성 및 재고 관리**

    - 로그인한 고객의 장바구니 상품을 기반으로 주문하며, 선택한 장바구니 상품 ID가 없으면 장바구니 전체 상품을 주문 대상으로 처리합니다. 
    - 주문 대상이 본인의 장바구니 상품인지 확인하고, 모든 상품의 재고를 검증한 후 재고를 선차감합니다.
    - 주문 생성 **전체 과정을 하나의 트랜잭션**으로 처리하여 하나의 상품이라도 재고가 부족하거나 예외가 발생하면 재고 차감 및 주문 생성을 모두 롤백합니다.

- **주문 상태 및 주문 상품 관리**
    - 주문번호는 서버에서 고유하게 생성하고 주문 상태를 결제 대기 상태로 초기화하며, 이후 상태 변경은 결제·취소 흐름을 통해 처리합니다.
    - 주문 상품에는 주문 당시 상품명·판매 가격·수량을 스냅샷으로 저장하여 이후 상품 정보가 변경되어도 주문 당시 정보를 유지합니다.
    - 주문 총액을 계산하여 동일한 금액의 결제 대기 데이터를 사전 생성하며, 주문 생성 시 장바구니는 유지하고 결제 성공 시점에 비웁니다.
    - 결제 실패 후 재시도하는 경우에는 새로운 주문을 생성합니다.

- **주문 조회 및 소유권 검증**

    - 로그인한 고객의 주문 목록을 최신순으로 조회하고 다른 고객의 주문은 노출하지 않습니다.
    - 주문 상세 조회 시 주문 정보 + 주문 상품 목록(스냅샷) + 결제 상태를 함께 반환합니다.
    - 주문 소유권을 검증하여 본인의 주문에만 접근할 수 있도록 제한합니다.

<br>

#### <span style="color:lightgreen">🛍️상품(Product)</span>

- **상품 조회 및 필터링**
    - 상품 목록 조회 시 카테고리,최소가격,최대 가격을 조건으로 필터링하여 상품 조회를 합니다.
    - 필터 조건은 필수가 아닌 선택값므로 아무 조건도 입력을 안할시 전체 상품 조회를 합니다.
    - 상품 목록은 최신 정렬을 하고 page,size을 이용하여 페이지네이션을 적용을 합니다.

- **상품 상세 조회 및 예외 처리**
    - 데이터베이스의 저장된 특정 상품의 정보를 상품ID를 통해 조회합니다.
    - 존재 하지 않은 상품 ID를 조회할 경우 404 Not Found를 반환을 하고 "저장되지 않은 상품입니다"라는 메시지를 클라이언트에게 반환을 합니다.
    -상품의 품절 여부는 **재고 수량이 0인지**를 기준으로 판단을 합니다.

### 개발 규칙 및 코드 컨벤션

#### 네이밍 규칙 (Naming Conventions)
- **클래스명**: `PascalCase` (예: `AdminService`)
- **메서드 및 변수명**: `camelCase` (예: `getAdmins`, `adminId`)
- **상수명**: `UPPER_SNAKE_CASE` (예: `MAX_PAGE_SIZE`)
- **DB 테이블 및 컬럼**: `snake_case` (예: `admin_role`, `created_at`)

#### 아키텍처 및 DTO
- **계층 분리**: `Controller` -> `Service` -> `Repository`의 3계층 구조를 준수합니다.
- **DTO 분리**: Entity를 뷰나 API에 직접 노출하지 않고, 별도의 `Request / Response DTO` 객체로 변환하여 사용합니다.
- **예외 처리**: 비즈니스 예외는 도메인별 커스텀 에러로 정의하고 `GlobalExceptionHandler`에서 `ApiResponse` 형식으로 일괄 처리합니다.

#### RESTful API 설계
- **URI 표기**: 소문자와 하이픈(`-`) 위주로 사용하며, 자원(Resource)은 복수형 명사로 표현합니다. (예: `/admins/{adminId}`)
- **HTTP 메서드**: 의미에 맞는 표준 메서드(`GET`, `POST`, `PUT`, `PATCH`, `DELETE`)를 엄격히 사용합니다.

#### 커밋 메시지 규칙 (Commit Convention)
- `feat` : 새로운 기능 추가
- `fix` : 버그 수정
- `docs` : 문서 수정
- `style` : 코드 포멧팅, 세미콜론 누락, 코드 변경이 없는 경우
- `refactor` : 코드 리펙토링
- `test` : 테스트 코드, 리펙토링 테스트 코드 추가
- `chore` : 빌드 업무 수정, 패키지 매니저 수정
